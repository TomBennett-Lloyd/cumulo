---
name: plan-issue
description: Plan a GitHub issue into executable chunks via the planner agent and post the plan to the issue. Use before starting any non-trivial ticket.
---

You are orchestrating the planning phase for one GitHub issue.

1. `gh issue view <n> --comments` — read the issue in full.
2. Model selection: planner runs on **Fable** (`model: 'fable'` — see CLAUDE.md Model tiers). First read `~/.local/state/claude-budget/mode` (missing file → `normal`): if it reads `conserve`, run it on Opus instead and note the downgrade in the plan comment.
3. Pull the main checkout first (`git -C <main-checkout> pull`). Worktrees are cut from a freshly fetched `origin/main`, but the planner reads the parked checkout — #178's planner drafted against a main that predated two merges, targeting a file one PR had renamed and re-creating a fixture another had already extracted, costing a full revision round. Then spawn the `planner` agent with: the full issue content, pointers to relevant code areas, and any constraints from the conversation. Do not pre-chew the plan for it.
4. Validate the returned plan before accepting:
   - every chunk names real files, has mechanically checkable acceptance criteria and a `Verify:` command;
   - a weaker-model agent could execute each chunk from its text alone;
   - `Depends on:` edges form a DAG, and **parallelism claims are disjoint in verification, not merely in `Files:`** — a chunk's acceptance can transiently mutate a sibling's file, or run a whole-repo `pnpm verify` while a sibling is mid-edit. Two chunk pairs on #356 were file-disjoint and still had to be serialised by the orchestrator after the plan claimed the parallel edge. Check what each chunk's acceptance touches and runs, not what it lists;
   - **a changed rule, value or procedure names every other site that states it** — `architecture.md` rule 9's question, asked at plan time rather than at review time. Nothing here used to ask it, and #368 spent three review cycles discovering that its gate, landed in only the two files the issue named, deadlocked the next `humanAlways` PR by construction. The plan's own sweep claim is not evidence for this: **a sweep asserted in a plan carries its command and its output, the way an acceptance criterion does, or it is not asserted.** #356's plan claimed a file family had been swept and needed no edit; it had not been, and that one false claim cost three review cycles of re-sweeping;
   - **every prescribed mutant is shown to bite.** `planner.md` already demands direction-soundness and non-equivalence; this is the check that the demand held, and it is not the same as asking whether a `Verify:` command exists. A mutation that cannot fail asserts nothing while looking exactly like one that works: #176's mutation 3 could never fail (the worker fallback chain reaches `script-src 'self'`) and an implementer found that out by running it, and 4 of 4 mutants predicted by the #327 batch's plan turned out wrong or unkillable when run. Either the plan cites a run that killed the mutant, or the chunk's criterion is "run this mutation and report what died" — never "this mutation will fail test X";
   - **literal code in a plan has cleared the real gate.** A pasted body invites literal application, and this repo's gate is `pnpm verify`, not `tsc`: #367's plan specified a helper body that typechecked and could not pass lint, forcing a mid-flight redesign of the chunk. Either the body has been run through `lint` and `typecheck`, or the chunk specifies shape and lets the implementer write it.
     If it falls short, send it back once with specific defects. If still short, escalate to the user.
5. Post the plan: `gh issue comment <n> --body-file <plan file>`. Apply label `planned` (`gh issue edit <n> --add-label planned`).
6. Check `.claude/workflow.json` → `planApproval`. If `mode` is `required` **or** the issue carries any label listed in `planApproval.alwaysRequiredFor` (e.g. `adr` — major decisions always get a human, even after graduation to `auto`): surface a plan summary and link to the user and STOP — do not `/execute` until the user approves. Log any plan feedback they give to `docs/review-feedback.md` (category `plan`) as you address it. If `auto`: proceed to `/execute` unless the plan's "Risks & open questions" contains questions only the user can answer — surface those first.

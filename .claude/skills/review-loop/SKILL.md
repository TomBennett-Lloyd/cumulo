name: review-loop
description: Iterate reviewer findings on the current branch until the quality bar is met, max 3 cycles. Systemic findings go to the tech-debt log instead of blocking. Ends by opening the PR.
---

You are orchestrating the quality loop on the current branch. Hard cap: **3 cycles**. The cap is what stops "exemplary quality" from becoming an infinite loop; the tech-debt log is where the overflow goes.

Per cycle:

1. **Confirm the branch is whole before dispatching**: `git status` clean, and every chunk in the plan's ledger ticked `committed` — on #177 the reviewer read a branch one commit short, because the orchestrator dispatched review straight off a chunk-completion notification without committing the wave. Then spawn the `reviewer` agent on the branch diff.
2. Partition its findings:
   - **FIX-NOW** → dispatch fixes to an `implementer` (batch related findings into one dispatch; trivial one-liners you may fix inline — with absolute paths, after confirming `pwd`, since a backgrounded command's `cd` does not persist and this shell has twice been found back in the main checkout, where even the locator greps read the wrong tree).
   - **SYSTEMIC** → append to `docs/tech-debt.md` in its entry format, with file refs and this PR as source. Do NOT attempt to fix them in this task.
3. Re-run checks (`pnpm verify`), next cycle.

Exit conditions:

- Reviewer returns `VERDICT: APPROVE` → done.
- Cap reached with findings outstanding: **correctness bugs must still be fixed — never merge a known bug, cap or no cap.** Remaining pure-quality FIX-NOWs get demoted to `docs/tech-debt.md` with a note that they were demoted at cap (this is signal for /retro: the bar and the cap are fighting).

Then:

4. Push branch; `gh pr create` — always pass `--head <branch>` explicitly, because it infers the head branch from the shell's cwd and so walks into the same non-persistent-`cd` trap as step 2 — twice now aiming a PR at main-into-main ("head branch main is the same as base"). Title references the issue (`Closes #n`), body summarizes what/why, links the plan comment, and notes any tech-debt entries this task added. Wait for CI green.
5. Classify the diff per `.claude/workflow.json`'s `merge.autoRule` / `merge.humanAlways`: **auto** (no source-code files — no `.ts`, `.tsx`, `.js`, `.mjs`, `.cjs`, `.sh`, `.py`, `.tf`, `.sql` — and nothing under `docs/adr/`) → merge (squash, delete branch) and run `/retro`. The merge sequence from here on is the merge owner's (top-level session; see `run-issue` when orchestration is delegated); a task-orchestrator stops at classification + label. Merge sequence under branch protection: `gh pr update-branch` FIRST, unconditionally, before the first checks watch — never treat a green watch as permission to skip it, because a green watch on a stale head is not a mergeable state, and the merge bounce costs a full second CI round to discover (#229 arrived conflicted, #241 arrived merely BEHIND; both bounced for the same skipped step). A conflict there in `docs/tech-debt.md` resolves as a union of changes, never a union of lines — see the `triage` skill. **Every conflict resolution ends with a mechanical marker sweep before its commit** — `command grep -n '^<<<<<<<\|^=======$\|^>>>>>>>' <each resolved file>` must return nothing — because the rest of `verify` cannot be trusted to catch a stray: prettier reformats a leftover `>>>>>>> origin/main` in markdown into innocent nested blockquotes, which is exactly how one shipped to `main` in #211's resolution and sat there until an unrelated planner read the file (#253). Then wait for the NEW head's checks to register before watching — a `gh pr checks --watch` issued immediately exits green-early on the old head's results (sleep ~60–90 s first, then `--watch`), then merge. **Every gating command in that chain reports its own exit code** — `gh pr update-branch`, the checks watch, `gh pr merge` alike: `cmd > out 2>&1; rc=$?; tail out; echo RC=$rc`, capturing `$?` immediately and never reading the exit of a `| tail` or `| grep` the command was piped through, since a pipe's exit status is its last command's. PR #224's conflict-blocked update-branch AND the failed merge that followed both read as success through a piped tail, caught only because the issue stayed open — the same class the `execute` skill's step 5 encodes for `pnpm verify`, reappearing in a different pipeline. **human** (any source code, or any ADR) → write this PR's `docs/review-feedback.md` entry ON THE BRANCH first (in the shape and vocabulary that log's own header declares — it owns the format, so read it there rather than from memory — and per `merge.mergeRitual`, even when the expected verdict is "approved, no changes") and push it, because that entry is both what the `merge-ritual-gate` job looks for and part of the diff the user is being asked to approve; then, on that head's green CI, add the `awaiting-review` label, notify the user with a one-paragraph review guide (what to look at, what decisions were made), and do NOT merge; continue with independent tickets. Entry before label, always: the label on an entry-less branch reddens the gate by construction, and nothing then goes green to notify on. When the user reviews: every substantive piece of feedback updates that on-branch entry in the very commit that responds to it (cycle cap still applies), and merge only after they approve — at merge the label comes off and nothing further is owed. After merge: `/retro`.
6. **Then decide this worktree's fate.** Continuing — a related follow-up that needs this worktree's local assets (warm `node_modules`, Terraform state, local overrides): `bash .claude/scripts/rebranch-worktree.sh <next-branch>`, which rebases onto updated `main` and keeps those assets. Finished: leave the worktree clean on its merged branch — that alone makes it reapable — and run `bash .claude/scripts/sweep-worktrees.sh` to collect dead siblings from earlier sessions. Never remove the worktree you are running in; the sweeper always skips its own cwd, and a later session's sweep collects yours.

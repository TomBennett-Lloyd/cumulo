name: review-loop
description: Iterate reviewer findings on the current branch until the quality bar is met, max 3 cycles plus a scoped confirmation pass on the final fix diff. Systemic findings go to the tech-debt log instead of blocking. Ends by opening the PR.
---

You are orchestrating the quality loop on the current branch. Hard cap: **3 cycles, plus a scoped confirmation pass on the final fix diff.** The cap is what stops "exemplary quality" from becoming an infinite loop; the tech-debt log is where the overflow goes. The confirmation pass is not a fourth cycle and does not extend the cap: the cap bounds **iteration on the branch**, while the pass reviews the fix commits the last cycle never saw, on that diff alone, under its own termination rule. Both are specified under Exit conditions — read them before deciding you are finished, because stopping at cycle 3 with unreviewed fixes on the branch is the specific failure this shape exists to prevent.

**Restatement ledger for this bound** (`architecture.md` rule 9). This list is a **floor, not a census** — it is what `command grep -rnE '3[ -]cycle|three[ -]cycle|cycles? <c>/3|≤ ?3 cycle' .claude docs CLAUDE.md` returned, classified; run it again before moving the bound rather than trusting the list.

- **Carriers — they state the live bound and must move with it**: the frontmatter `description` above; `.claude/agents/task-orchestrator.md`'s stop-list paragraph and both its report templates (the TASK REPORT verdict line and the RETRO HANDOVER review-loop line); `docs/design/task-orchestrator.md`'s ownership-split role table, its one-review-loop-per-batch paragraph, its bounce-round ownership item, its risk table's sick-batch-member row, and its mirrored copies of those same two templates; and `CLAUDE.md`'s Workflow bullet, which is a `humanAlways` path and therefore moves only by owner decision — it currently states the pre-amendment bound and is the subject of an open proposal.
- **Not carriers — two classes, so a new instance of either needs no edit.** (a) Past-tense narration of what a specific past ticket did (`.claude/agents/reviewer.md`, `docs/friction-log.md`, `docs/review-feedback.md` and `docs/design/design-principles.md` all hold instances): rule 9 permits historical claims in past tense, and they stay true whatever the bound becomes. (b) Pointers that carry no number, such as `docs/design/task-orchestrator.md`'s humanAlways-feedback bullet. Anything the sweep returns that is neither of those is a carrier you have just found.

The `/3` denominator in the report templates is deliberate and stays: **the confirmation pass is not a cycle**, so it does not move the denominator — it gets its own slot in the same templates.

Per cycle:

1. **Confirm the branch is whole before dispatching**: `git status` clean, and every chunk in the plan's ledger ticked `committed` — on #177 the reviewer read a branch one commit short, because the orchestrator dispatched review straight off a chunk-completion notification without committing the wave. Then spawn the `reviewer` agent on the branch diff — **and name, in cycle 1's dispatch, the prose you wrote into that diff yourself**: `docs/tech-debt.md` entries, `discovered` issue bodies, the PR body. Chunk work reaches the reviewer having already passed implementer → your own verification; that prose reaches it having passed nothing, and it is the only thing in the diff with no author but you. Twice now the late-cycle correctness defects have all been in it (#334 cycle 3, and the previous retro's own loop), and both times they were confident claims about the repo's own history that the repo's own history falsified — so an entry asserting repo _practice_ cites the commits that evidence it, and the reviewer is asked to check those commits rather than the claim's plausibility. Cycle 1, not cycle 3: reached at the cap, this prose is exactly what a demotion decision buries.
2. Partition its findings:
   - **FIX-NOW** → dispatch fixes to an `implementer` (batch related findings into one dispatch; trivial one-liners you may fix inline — with absolute paths, after confirming `pwd`, since a backgrounded command's `cd` does not persist and this shell has twice been found back in the main checkout, where even the locator greps read the wrong tree).
   - **SYSTEMIC** → append to `docs/tech-debt.md` in its entry format, with file refs and this PR as source. Do NOT attempt to fix them in this task.
3. Re-run checks (`pnpm verify`), next cycle.

Exit conditions:

- Reviewer returns `VERDICT: APPROVE` → done.
- Cap reached with findings outstanding: **correctness bugs must still be fixed — never merge a known bug, cap or no cap.** Remaining pure-quality FIX-NOWs get demoted to `docs/tech-debt.md` with a note that they were demoted at cap (this is signal for /retro: the bar and the cap are fighting). **One exception to "pure quality": a documented trap that would recreate the bug this loop just fixed is not quality, it is the bug on a delay.** #398's cycle 3 found a comment conceding that an absolute grid tolerance "would work", false in exactly the direction that reintroduces the cycle-1 correctness bug — a maintainer who believed it would have shipped the bug back — so it was fixed at cap rather than logged.
- **CAP-REACHED still owes the shipped diff a verdict.** A cap cycle that ends ITERATE-then-fixed ships fixes no reviewer ever saw, so `merge.reviewedSourceRule`'s APPROVE can never be earned and the PR dead-ends into human review for a procedural reason. On CAP-REACHED, dispatch a reviewer **scoped strictly to the fix commits made since the last reviewer looked**, for an APPROVE/ITERATE verdict on that diff alone: the cap bounds iteration on the branch, not review of the fix. Correctness findings it returns are fixed and re-confirmed the same way. Closed four PRs this way already (#391, #395, #398, #400).
- **The confirmation cycle carries its own termination rule, or it substitutes an unbounded loop for a capped one.** Instruct the confirmation reviewer to classify diminishing findings as SYSTEMIC, reserving FIX-NOW for what would mislead a maintainer into a **behavioural** mistake. #398 spent three confirmation rounds re-deriving ever-more-careful figures that the next round falsified; round 4's dispatch carried exactly that instruction and returned a verdict instead of a seventh round. Its convergent move is worth knowing when you write the fixes: **when a fix keeps minting false claims, delete the derived figures rather than track them** — an enumeration claiming completeness is falsifiable by one more carrier, while one that declares itself a floor and names its sweep is not.

Then:

4. Push branch; `gh pr create` — always pass `--head <branch>` explicitly, because it infers the head branch from the shell's cwd and so walks into the same non-persistent-`cd` trap as step 2 — twice now aiming a PR at main-into-main ("head branch main is the same as base"). Title references the issue (`Closes #n`), body summarizes what/why, links the plan comment, and notes any tech-debt entries this task added. Then wait for CI green — with two branches before the watch:

   - **Check mergeability first.** `gh pr view <n> --json mergeStateStatus`: a `DIRTY` PR has no computable merge ref, so GitHub never queues its `pull_request` workflows at all and `gh pr checks` reports "no checks reported" — indistinguishable from a queue that has not started. Four tickets polled through that state before diagnosing it (#393, #395, #366, #398; one of them seven times over eleven minutes). Resolve the conflict, push, then watch. "Twice silent" is a mergeability check, never a longer wait.
   - **A red lane may be re-run once, and only for a signature an open issue already owns.** The practice has been applied often enough to be the de facto rule and was written down nowhere: re-run once for that specific known-flaky signature, and treat a second failure with the same signature as real. Anything else red is real on the first failure. Name the issue in the report when you use it (`#382` is the live one; `#303` was the last, fixed by #394) — a re-run whose signature belongs to no open issue is a defect being wished away.

5. Classify the diff per `.claude/workflow.json`'s `merge.autoRule` / `merge.humanAlways`: **auto** (no source-code files — no `.ts`, `.tsx`, `.js`, `.mjs`, `.cjs`, `.sh`, `.py`, `.tf`, `.sql` — and nothing under `docs/adr/`) → merge (squash, delete branch) and run `/retro`. The merge sequence from here on is the merge owner's (top-level session; see `run-issue` when orchestration is delegated); a task-orchestrator stops at classification + label. Merge sequence under branch protection: `gh pr update-branch` FIRST, unconditionally, before the first checks watch — never treat a green watch as permission to skip it, because a green watch on a stale head is not a mergeable state, and the merge bounce costs a full second CI round to discover (#229 arrived conflicted, #241 arrived merely BEHIND; both bounced for the same skipped step). **Run every rebase in this repo as `git -c core.commentChar=';' rebase …`**: every commit subject here begins `#<issue>`, and git's default message cleanup reads a leading `#` as a comment and silently **deletes the subject line** (#321 lost one that way). Then check the result — `git log --format='%s%n%b' <range>` must show every subject intact and no `^#` line inside a body, because the `commentChar` repair preserves git's own `# Conflicts:` block into the message, which is the defect that swap introduces (#366's confirmation pass caught it). A conflict there in `docs/tech-debt.md` resolves as a union of changes, never a union of lines — see the `triage` skill — with two clauses that rule alone does not give you. **A deletion on either side is authoritative**: the union preserves both sides' _additions_, and an entry the other side removed is never reinstated, because resurrection passes the naive "did the union lose anything?" invariant and reports success (#368's third curation would have brought back the D7 entry #366 deliberately deleted). And **capture the heading and redirect-row sets of base, main and branch _before_ rebasing**, which turns the resolution from judgement into arithmetic — expected = main's headings − deletions + your additions, checked as a count plus `comm`/`grep -vxFf` in both directions. Four curations have run it with empty output on both sides (#395, #398 twice, #366); it is the mechanical answer to the line-union failure mode. **Every conflict resolution then ends with a mechanical marker sweep before its commit** — `command grep -nE '^(<<<<<<<|=======|>>>>>>>)' <each resolved file>` must return nothing, paired with `git diff --check`, which detects all three markers independently. Write the sweep as ERE and never as a BRE alternation: in `'^<<<<<<<\|^=======$\|^>>>>>>>'` the `$` anchors only at the end of the whole pattern, so on BSD grep (this machine's default) that branch searches for the literal text `=======$` and a lone separator is invisible — reproduced on a fixture holding all three markers, which returned two and exited 0 (#396). That lone `=======` is both the likeliest leftover of a sloppy resolution and the one prettier can launder into innocent nested blockquotes, which is exactly how one shipped to `main` in #211's resolution and sat there until an unrelated planner read the file (#253). Then wait for the NEW head's checks to register before watching — a `gh pr checks --watch` issued immediately exits green-early on the old head's results (sleep ~60–90 s first, then `--watch`), then merge. **Every gating command in that chain reports its own exit code** — `gh pr update-branch`, the checks watch, `gh pr merge` alike: `cmd > out 2>&1; rc=$?; tail out; echo RC=$rc`, capturing `$?` immediately and never reading the exit of a `| tail` or `| grep` the command was piped through, since a pipe's exit status is its last command's. PR #224's conflict-blocked update-branch AND the failed merge that followed both read as success through a piped tail, caught only because the issue stayed open — the same class the `execute` skill's step 5 encodes for `pnpm verify`, reappearing in a different pipeline. **human** (any source code, or any ADR) → write this PR's `docs/review-feedback.md` entry ON THE BRANCH first (in the shape and vocabulary that log's own header declares — it owns the format, so read it there rather than from memory — and per `merge.mergeRitual`, even when the expected verdict is "approved, no changes") and push it, because that entry is both what the `merge-ritual-gate` job looks for and part of the diff the user is being asked to approve; then, on that head's green CI, add the `awaiting-review` label, notify the user with a one-paragraph review guide (what to look at, what decisions were made), and do NOT merge; continue with independent tickets. Entry before label, always: the label on an entry-less branch reddens the gate by construction, and nothing then goes green to notify on. When the user reviews: every substantive piece of feedback updates that on-branch entry in the very commit that responds to it (cycle cap still applies), and merge only after they approve — at merge the label comes off and nothing further is owed. After merge: `/retro`.
6. **Then decide this worktree's fate.** Continuing — a related follow-up that needs this worktree's local assets (warm `node_modules`, Terraform state, local overrides): `bash .claude/scripts/rebranch-worktree.sh <next-branch>`, which rebases onto updated `main` and keeps those assets. Finished: leave the worktree clean on its merged branch — that alone makes it reapable — and run `bash .claude/scripts/sweep-worktrees.sh` to collect dead siblings from earlier sessions. Never remove the worktree you are running in; the sweeper always skips its own cwd, and a later session's sweep collects yours.

---
name: execute
description: Execute a planned issue by dispatching plan chunks to implementer sub-agents, independently verifying each result, and keeping the plan status updated on the issue.
---

You are orchestrating execution of an approved plan (in the issue's comments). Your context stays clean: sub-agents do the work; you verify, sequence, and re-plan.

1. **Worktree, always**: `git worktree add .claude/worktrees/<n>-<slug> -b <n>-<slug> origin/main`. Every task gets its own worktree even when it is the only one running — the main checkout stays on `main` so concurrent tasks, verification, and `/burn-backlog` never contend for it. Task-local untracked state (Terraform `backend.hcl`, `.terraform/`, local overrides) lives in that worktree for the task's lifetime. Never work on `main`. A fresh worktree gets its own `node_modules` from the SessionStart hook (`.claude/hooks/ensure-deps.sh`); if it is absent, run `pnpm install --frozen-lockfile` in the worktree yourself. To continue in a worktree whose previous task has already merged, reuse it instead of creating another: `bash .claude/scripts/rebranch-worktree.sh <n>-<slug>` rebases it onto updated `main` and keeps `node_modules` warm. For Terraform tasks, export `TF_PLUGIN_CACHE_DIR=~/.terraform.d/plugin-cache` (create the directory once) before `terraform init` — a fresh worktree otherwise re-downloads providers and can stall a timeboxed command.
2. **Load the plan**; compute dependency waves and post a **chunk ledger** comment on the issue: every chunk ID in the plan, each with `dispatched / committed / verified` checkboxes. The ledger — not your memory — is the record of what is outstanding; update it as each state changes. (An 8-chunk wave on #19 never dispatched one of its chunks; hand-tracking across two concurrent tickets was the whole cause.) Post it in the same action as wave 1's dispatch rather than as an earlier standalone step — dispatching wave 1 with no ledger up is the failure mode, and a standalone step is exactly what an orchestrator context compaction drops: #165 and #157 both ran their waves on a ledger reconstructed late, where the commit record happened to be a complete substitute and will not always be. Chunks in the same wave with no file overlap run in parallel — spawn their `implementer` agents in a single message.
3. **Dispatch** each chunk with: the chunk's full text verbatim, the plan's Context section, and nothing else it doesn't need.
4. **On each return, by status**:
   - `DONE` → verify independently: run the chunk's `Verify:` command yourself and spot-check the diff against each acceptance criterion. Trust but verify — an agent's own report is a claim, not evidence. If the chunk has a browser surface, a green suite is not evidence either: dispatch the `browser-smoke` agent (synchronously — read its dispatch contract) and take its measurement.
   - `PARTIAL` / `BLOCKED` → update the plan: minor adjustment inline, or re-run the planner for structural changes. Record what changed and why as an issue comment before re-dispatching.
   - `STRUGGLING` → read `~/.local/state/claude-budget/mode` (missing file → `normal`); spawn the `consultant` agent (Fable, or Opus if conserving — note it) with the implementer's full report. Re-dispatch the SAME chunk to a fresh `implementer` with the consultant's guidance attached. The consultant never implements.
   - `DISCOVERED:` items → `gh issue create --label discovered` for each (or comment on an existing issue). Never act on them in this task.
   - **Transient API failure in a parallel dispatch batch** → before re-dispatching anything, verify WHICH call actually failed by matching the surviving returns against each dispatch's description. Re-dispatching a chunk that is still running plants a duplicate in the same worktree; the implementer's pre-existing-files guard makes the duplicate return BLOCKED, but the correct move is not to create it.
5. **After each wave**: run `pnpm verify` yourself — only the settled tree is evidence, since a mid-wave red can be a sibling's in-flight file. **The verdict is the captured exit code** (`pnpm verify; echo $?`), never a grep over the output: a `| grep | head` pipeline reports the grep's status as the composite's, and truncated a failed `format:check` into a green on #166. Read the `verify root:` line it prints first and confirm it names THIS task's worktree and branch; a stale shell cwd has twice produced a green run, with another branch's test counts, against a different tree. **A composite that aborted early is not a full run**: `pnpm verify` chains its legs with `&&` and stops at the first failure, so one known-red package masks every gate behind it — when a run exits on an expected failure, run the skipped legs directly (`pnpm typecheck`, `pnpm test`, the `check:*` scripts, `pnpm format:check`) before calling anything green. #122 C1 read "green except the expected failure" twice over a `format:check` defect that had never run. Then **you** commit the wave (implementers never touch git — see `implementer.md`) with a descriptive message referencing the issue, and tick the ledger. **A consistency edit rides its own commit, never a merge commit** — a mechanical fixup staged into a merge appears in neither parent's diff, so review cannot see it at all (#16 hid a hindcast lint-script edit that way).
6. **All chunks done** → assert every chunk ID in the plan is ticked `verified` in the ledger, naming any that are not → run `pnpm verify` at repo root → invoke `/review-loop`.

# Tech-debt log

A **buffer, not an archive**. `/review-loop` appends SYSTEMIC findings here instead of iterating on them; `/triage` periodically clusters entries, files root-cause GitHub issues, and **deletes** what it captured. A long-lived entry here means triage is overdue.

Entry format:

```
## YYYY-MM-DD — short title
- Where: file/module references
- What: the pattern or problem (symptom AND suspected root cause if known)
- Source: PR/issue #
```

Pointers must survive unrelated edits: cite **files and symbol or section names** (function names, headings, config keys, script names) — never bare line numbers, and never a copied code literal unless the literal itself is the finding. An entry that pins its claim to `file.sh`:42 sends its reader to whatever happens to sit at line 42 months later. Applies to entries dated 2026-07-31 onward; the back catalogue is retrofitted opportunistically, whenever an entry is edited for any other reason.

## 2026-07-30 — `aws_budgets_budget.cost_types` left at AWS defaults

- Where: `infra/bootstrap/budget.tf` (`aws_budgets_budget.monthly_cost_ceiling`)
- What: no `cost_types` block, so the budget uses the AWS defaults, which subtract credits and refunds. On an account carrying promotional credits the meter can therefore run well past $100/month of gross usage while net cost stays under threshold and nothing alerts — the alarm reports what will be billed, not what is being consumed. That is a defensible reading of "cost ceiling" for a project whose ceiling is about the bank balance, and it is the current deliberate choice; it stops being defensible the moment credits land on the account, because the whole point of the ceiling is to catch runaway usage _before_ it is expensive. Revisit if credits appear (or before any AWS-credits programme is used for this project): either add `cost_types { include_credit = true, include_refund = false }`, or add a second usage-oriented budget beside the billed-cost one. Not a fix for this diff — it is a policy decision about what the number means, and it wants the account's credit state as an input.

It is a parked decision with an external trigger (credits appearing on the account), not debt to clear — an open issue would be picked up by backlog burning and correctly do nothing. ## 2026-07-31 — A hook that cannot read its own events disables edit-time lint silently

- Where: `.claude/hooks/hook-context.sh` (`hook_event_field`), and both callers — `.claude/hooks/post-edit-check.sh`, `.claude/hooks/ensure-deps.sh`
- What: `hook_event_field` returns empty for three enumerated reasons (absent field, non-string value, unparseable JSON), all of which honestly mean "this event does not name anything to act on". There is a fourth it does not enumerate and cannot distinguish: `python3` missing, or crashing, or shadowed on PATH. That one does not mean "nothing to act on", it means **no event can be read at all** — so `post-edit-check` silently stops linting every edit for the rest of the session and `ensure-deps` silently stops preparing every worktree. Extends #102's tool-assumptions primitive, which stops at `.claude/scripts` (its acceptance criterion greps only that directory) and describes a failure that is "safe (exit 2 everywhere) but total". The hook layer is the worse shape: it does not refuse, it **degrades into a legitimate-looking no-verdict**, which is the "gate that stops firing produces no output" class of #101. Wants two decisions taken together, because either alone is half a fix: a `command -v python3` preflight that fails loudly instead of returning empty, and a position on whether a no-verdict outcome should be visible at all — post-edit-check's silence is deliberate (a scratchpad edit outside the repo must not chatter on every keystroke), so "log every no-verdict" is not obviously right, and the answer probably has to distinguish "nothing to judge" from "cannot judge". Same question applies to `git` and `pnpm`, which the hooks also assume.
- Source: #74 review cycle 1

Migration is mechanical but touches all seven files, so it is its own change, not a rider on a hook fix.

## 2026-07-31 — Harnesses capture `2>&1`, so they cannot tell a success report from a failure report

- Where: `.claude/scripts/hook-tree-resolution.test.sh` (`run_post_edit`, `run_ensure_deps`, and the inline working-directory-fallback case); the same `2>&1` idiom in the other six harnesses
- What: merging the streams was convenient — one variable to assert on — but it discards a distinction the scripts under test deliberately encode. `ensure-deps.sh` writes "ran pnpm install, deps are ready" to **stdout** and "install failed" to **stderr**; a harness capturing `2>&1` and asserting the root path appears cannot tell which of the two it got. The consequence is concrete in the #74 diff: the ensure-deps cases provoke the _failure_ branch (deliberately, to stay offline and fast), and the success branch — the one that runs in every fresh worktree — has no case at all, with nothing in the harness able to notice the gap. Same blind spot in `post-edit-check`, where exit 2 plus stderr is the contract that makes Claude Code surface the message to the agent; a change routing the report to stdout would keep every case green and silently end the feedback loop the hook exists for. That silent-green shape puts it in #101's family, and the fix belongs with the harness library above rather than as a local patch: `expect_stdout` / `expect_stderr` capturing the two streams separately, then a success-branch case for `ensure-deps` built on a fixture whose install genuinely succeeds (an empty workspace with a matching lockfile, still offline).
- Source: #74 review cycle 1

## 2026-07-31 — `check-supply-chain-policy.sh` reads YAML by line shape, so a block scalar can forge a justification

- Where: `.claude/scripts/check-supply-chain-policy.sh`, the comment-run branch of the parse loop; `check-supply-chain-policy.test.sh` case "lines indented deeper than the entry level are continuations, not entries"
- What: the gate decides an opt-out is justified by looking at the contiguous run of `#`-leading lines directly above it. It has no notion of block scalars, so a `#`-leading line _inside_ a `>-` or `|` scalar is content, not a comment, and the gate counts it as one. Demonstrated: a `minimumReleaseAgeExclude` whose first entry is a folded scalar containing a `#` line makes the gate report "2 opt-out entr(y/ies), all justified" for a manifest whose **second** entry has no comment anywhere near it — exit 0 on an unexplained supply-chain exemption, which is the exact silent-green the gate's own header rules out. The blind spot is reachable only because the harness case above blesses folded scalars, so the shape is nominally supported rather than refused; the honest options are block-scalar tracking (a state machine keyed on the `>`/`|` indicator and the scalar's indentation) or a refusal on any scalar indicator inside a guarded block, which reverses that case's premise. Both are parser-level work, and the second is a scope call about how much YAML a dependency-free gate should pretend to understand — neither belongs in the cycle that found it. Same family as the inline-flow-collection hole fixed in #92 (a shape the line reader could not see, reported as clean); that one was fixed in place because the refusal was five lines, this one is not.
- Source: #92 review cycle 1

## 2026-07-31 — Supply-chain gate asserts the manifest, but pnpm resolves policy from four places

- Where: `.claude/scripts/check-supply-chain-policy.sh` (the `release_age` / `release_age_strict` verdict); its scope-limit header paragraph
- What: the gate proves `pnpm-workspace.yaml` sets `minimumReleaseAge` and `minimumReleaseAgeStrict`, and reports "OK" — but pnpm reads those settings from CLI flags, `pnpm_config_*` environment variables and the global `config.yaml` as well, all of which outrank the manifest. `pnpm_config_minimum_release_age_strict=false` exported in a CI runner or a developer's shell puts pnpm back into the loose auto-exclude mode #92 exists to kill, with `pnpm verify` green throughout. The gap is now stated in the script header (so the OK line is not read as more than it is) but not closed. Closing it means asking pnpm for its **effective** configuration at gate time — `pnpm config get minimumReleaseAgeStrict` or the JSON from `pnpm config list` — which drags a pnpm invocation into a script whose "no dependencies: bash only, no pnpm, no network" property is load-bearing: it is what lets the gate run in the harness against throwaway fixtures with no install behind them. So it is a real scope decision (a second gate that does depend on pnpm? a preflight in `verify:root`? accept and document?), not an oversight, and it wants deciding rather than patching. Related: the same precedence question decides whether a future pin-versions policy (#108) can be enforced from the manifest at all.

## 2026-07-31 — Cycle rotation advances one location per hour, not one window

- Where: `apps/ingestion/src/locations.ts` (`rotationOffset`), consumed by `runCycle` in `apps/ingestion/src/cycle.ts`
- What: the offset is `floor(now / hour) % length`, so consecutive cycles shift the served window by **one location**, not by `maxLocations`. For a fleet of `n` above the cap, full coverage therefore takes `n` hours rather than `ceil(n / cap)`, and any individual location waits `n − cap` hours between visits. With a 48-hour stored horizon, continuous forecast coverage holds only while `n − cap ≤ 48`, i.e. to about 148 locations at the current cap of 100 — beyond that a location's stored horizon expires before its next visit and the fleet develops permanent gaps that nothing reports, since a deferral is (correctly) not a failure. Stepping the offset by `maxLocations` instead of by 1 fixes it at no cost and makes the wait `ceil(n / cap)` hours as intended. Not binding today — committed scale is ~30 locations (ADR 0002 "Assumed scale") against a cap of 100, so the cap never engages — which is exactly why it wants recording rather than fixing mid-review: the decision belongs with #17's visitor-site contract and #29's fleet-size cap, where "how large may the fleet get" is actually settled. The PR body for #115 initially claimed the `ceil(n / cap)` behaviour, which is the arithmetic the code should have had.
- Source: #115 review cycle 1

## 2026-07-31 — One ingestion alarm now stands for two unrelated operator questions

- Where: `infra/ingestion/alarms.tf` (`aws_cloudwatch_metric_alarm.ingestion_errors`), against `CycleFailedError` in `apps/ingestion/src/handler.ts`
- What: the alarm fires on the Lambda's `Errors` metric, and the handler throws whenever `failed > 0`. After #115 that count spans two conditions an operator responds to differently: a location that genuinely failed (rate limit, malformed body, adapter throw — investigate the location), and a cycle that exhausted its time budget and stopped starting locations (`skippedForDeadline > 0` — investigate the _effects_, because a healthy cycle finishes in seconds). The third condition, a fleet larger than the cap, was folded into the same count in the first draft of #115 and is now excluded by design: deferrals are counted in `deferred` and do not throw, precisely because an over-cap fleet would otherwise page every hour forever. The alarm description now spells out how to tell the remaining two apart, which is a mitigation and not a fix — routing and severity are still one channel. Splitting them means a metric filter on the `ingestion.cycle.summary` entry's `skippedForDeadline` field with its own alarm and its own severity, which is fleet-operations territory and belongs with #29 rather than being decided inside a debt-burn PR.
- Source: #115 review cycle 1

## 2026-07-31 — The ingestion time budget prices `Retry-After` at zero on both AWS paths

- Where: `apps/ingestion/src/cycle-budget.ts` (`STORE_SEND_WORST_MS`, `PUBLISH_WORST_MS`, and the `CYCLE_DEADLINE_MS` identity)
- What: the budget multiplies out attempt counts, pinned request timeouts and the two backoff curves, and every term is imported rather than remembered. One term is missing: the smithy standard retry strategy honours a server-supplied retry hint, extending any single retry by up to an extra 5,000 ms beyond the computed delay (verified in the installed `@smithy/core` 3.31.1). Neither DynamoDB nor SQS sends `Retry-After` in normal operation, so the term is zero in practice — but it is not zero by construction, and `CYCLE_DEADLINE_MS = INGESTION_LAMBDA_TIMEOUT_MS − LOCATION_WORST_MS − SHUTDOWN_MARGIN_MS` has **no slack at all**: the identity is exact, so any unpriced term makes the function timeout reachable rather than unreachable by exactly that amount. The caveat is now stated in the module header so the claim is not read as stronger than it is. Closing it properly is a choice between pricing the hint (up to `5,000 × retries` per effect, which roughly doubles `LOCATION_WORST_MS` and halves the deadline for a term that never fires) and giving the identity explicit slack instead — a budgeting decision worth taking alongside the stacked-retry reduction in #122, which moves `LOCATION_WORST_MS` in the opposite direction and would pay for it. A second unpriced term of the same shape, found in review cycle 2: `requestTimeout` bounds the time to the **first response**, not the whole attempt — the timer is cleared when the `response` event fires, which is when headers arrive and the body is still an open stream, and neither client sets `socketTimeout`. So a response whose headers arrive and whose body then stalls is bounded by nothing on either path, and `STORE_SEND_WORST_MS` / `PUBLISH_WORST_MS` are strictly bounds on time-to-first-response rather than on an attempt. Low probability for these small single-chunk API responses, and setting `socketTimeout` is not obviously right (it is an inactivity timer, so it fires on slow-but-progressing responses too) — but it is the same zero-slack problem: the identity is exact, so an unpriced term makes the function timeout reachable by however long a stalled body runs. The honest fix is the same budgeting decision as above — price an inactivity term or give the identity explicit slack — and the reduction in #122 is what pays for either.
- Source: #115 review cycles 1 and 2

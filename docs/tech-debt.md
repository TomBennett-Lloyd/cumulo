Entry format:

```
## YYYY-MM-DD — short title
- Where: file/module references
```

Pointers must survive unrelated edits: cite **files and symbol or section names** (function names, headings, config keys, script names) — never bare line numbers, and never a copied code literal unless the literal itself is the finding. ## 2026-07-30 — `aws_budgets_budget.cost_types` left at AWS defaults

## 2026-07-31 — `check-supply-chain-policy.sh` reads YAML by line shape, so a block scalar can forge a justification

- Where: `.claude/scripts/check-supply-chain-policy.sh`, the comment-run branch of the parse loop; `check-supply-chain-policy.test.sh` case "lines indented deeper than the entry level are continuations, not entries"
- What: the gate decides an opt-out is justified by looking at the contiguous run of `#`-leading lines directly above it. ## 2026-07-31 — Skill score compares two RMSEs computed over different sample sets

- Where: `runHindcast` and `baselineRmseKw` in `packages/hindcast/src/hindcast.ts`; `skillScore` and `errorMetricsSchema` in `packages/shared/src/metrics.ts`
- What: the model RMSE is taken over `replay ∩ in-period observations`, while the baseline RMSE is taken over `shifted observations ∩ in-period observations` — two inner joins with different left operands, so the two numbers routinely score different instants. The gap is not marginal: the `draws the first day of the period from observations made before it` case in `hindcast.test.ts` compares 48 model pairs against 48 baseline pairs in one arm and against 24 in the other, and the published `skillScore` moves accordingly. The honest fixes both cross the approved plan's spec: either restrict both series to the instants where model, baseline and observation all exist (changes the published numbers, and changes what a run with no run-up day reports), or keep the current arms and add a `baselineSampleCount` field so the asymmetry is at least visible. That is an `errorMetricsSchema` change, which is #20's comparison payload as well as this package's, so it wants deciding once for both rather than being settled inside a hindcast runner.

## 2026-07-31 — Cycle rotation advances one location per hour, not one window

- Where: `apps/ingestion/src/locations.ts` (`rotationOffset`), consumed by `runCycle` in `apps/ingestion/src/cycle.ts`
- What: the offset is `floor(now / hour) % length`, so consecutive cycles shift the served window by **one location**, not by `maxLocations`. For a fleet of `n` above the cap, full coverage therefore takes `n` hours rather than `ceil(n / cap)`, and any individual location waits `n − cap` hours between visits. With a 48-hour stored horizon, continuous forecast coverage holds only while `n − cap ≤ 48`, i.e. to about 148 locations at the current cap of 100 — beyond that a location's stored horizon expires before its next visit and the fleet develops permanent gaps that nothing reports, since a deferral is (correctly) not a failure. Stepping the offset by `maxLocations` instead of by 1 fixes it at no cost and makes the wait `ceil(n / cap)` hours as intended. Not binding today — committed scale is ~30 locations (ADR 0002 "Assumed scale") against a cap of 100, so the cap never engages — which is exactly why it wants recording rather than fixing mid-review: the decision belongs with #17's visitor-site contract and #29's fleet-size cap, where "how large may the fleet get" is actually settled. The PR body for #115 initially claimed the `ceil(n / cap)` behaviour, which is the arithmetic the code should have had.

## 2026-07-31 — The ingestion time budget prices `Retry-After` at zero on both AWS paths

- Where: `apps/ingestion/src/cycle-budget.ts` (`STORE_SEND_WORST_MS`, `PUBLISH_WORST_MS`, and the `CYCLE_DEADLINE_MS` identity)
- What: the budget multiplies out attempt counts, pinned request timeouts and the two backoff curves, and every term is imported rather than remembered. One term is missing: the smithy standard retry strategy honours a server-supplied retry hint, extending any single retry by up to an extra 5,000 ms beyond the computed delay (verified in the installed `@smithy/core` 3.31.1). Neither DynamoDB nor SQS sends `Retry-After` in normal operation, so the term is zero in practice — but it is not zero by construction, and `CYCLE_DEADLINE_MS = INGESTION_LAMBDA_TIMEOUT_MS − LOCATION_WORST_MS − SHUTDOWN_MARGIN_MS` has **no slack at all**: the identity is exact, so any unpriced term makes the function timeout reachable rather than unreachable by exactly that amount. The caveat is now stated in the module header so the claim is not read as stronger than it is. Closing it properly is a choice between pricing the hint (up to `5,000 × retries` per effect, which roughly doubles `LOCATION_WORST_MS` and halves the deadline for a term that never fires) and giving the identity explicit slack instead — a budgeting decision the stacked-retry reduction in #122 has now paid for rather than one waiting on it: that reduction landed, `LOCATION_WORST_MS` is 74,700 ms (was 146,700) and `CYCLE_DEADLINE_MS` 220,300 ms (was 148,300), so the headroom to price the hint or to grant the identity explicit slack exists. Which of the two to take is still open, which is why this entry is. A second unpriced term of the same shape, found in review cycle 2: `requestTimeout` bounds the time to the **first response**, not the whole attempt — the timer is cleared when the `response` event fires, which is when headers arrive and the body is still an open stream, and neither client sets `socketTimeout`. So a response whose headers arrive and whose body then stalls is bounded by nothing on either path, and `STORE_SEND_WORST_MS` / `PUBLISH_WORST_MS` are strictly bounds on time-to-first-response rather than on an attempt. Low probability for these small single-chunk API responses, and setting `socketTimeout` is not obviously right (it is an inactivity timer, so it fires on slow-but-progressing responses too) — but it is the same zero-slack problem: the identity is exact, so an unpriced term makes the function timeout reachable by however long a stalled body runs. The honest fix is the same budgeting decision as above — price an inactivity term or give the identity explicit slack — and #122's reduction is what paid for either. A third term of the same shape, surfaced while resolving a test-bound question in #122: per-attempt real wall-clock overhead — connecting, signing, serialising, event-loop scheduling — measured at roughly 15–70 ms per command during #122's C1, and priced at zero here because every term above it is a configured timeout or a backoff cap rather than anything measured. What #122 changed is the regime, not the term. Under the old stacked curve the printed worst case was approached only when three independent jitter draws all landed near their caps at once, and that concentration made the overhead statistically unobservable; with the curve collapsed to a single retry, one near-max draw plus tens of milliseconds of overhead is enough to exceed `STORE_SEND_WORST_MS` on the path where every attempt times out. Same fix menu as the two terms above — price it or give the identity explicit slack — and the same reduction pays for it, so it is recorded here rather than filed separately.
- Source: #115 review cycles 1 and 2; third term from #122

## 2026-07-31 — `check-infra-mirrors.sh` reads Terraform by line shape, so a heredoc body can pose as an attribute

## 2026-08-01 — One client-wide attempt budget now serves two failure regimes with different owners

- Where: `STORAGE_MAX_ATTEMPTS` in `packages/storage/src/client.ts`; `drainBatches` and `defaultBatchPolicy` in `packages/storage/src/batch.ts`; `queryAllPages` in `packages/storage/src/adapters/storage-adapter-base.ts` and its callers in `adapters/series/series-adapter.ts`, `adapters/site/site-adapter.ts`, `adapters/metrics/metrics-adapter.ts`, `adapters/weather/weather-adapter.ts`; the `TransactWriteCommand` send in `adapters/weather/weather-adapter.ts` and the retry-layer inventory in `client.ts`'s `STORAGE_MAX_ATTEMPTS` doc block; ADR 0002 (`docs/adr/0002-storage-split.md`), section "The failure mode, stated honestly"
- What: #122 collapsed `STORAGE_MAX_ATTEMPTS` to 2 on the reasoning that the drain layer owns throttling — which is true of the path the issue was about. `BatchWriteItem` throttling arrives as `UnprocessedItems` on an HTTP 200, and `drainBatches` re-sends those under its own three-attempt curve, so the SDK layer there is left with transport blips and one retry is the right budget. That carve-out is narrower than it first looks, though: a **wholly** declined `BatchWriteItem` or `BatchGetItem` does not answer with an empty result and a full `UnprocessedItems` map — it throws `ProvisionedThroughputExceededException` outright, so the drain layer never engages and the SDK's single retry is the entire throttle budget on batch paths too, exactly as on the single-request ones. The batch case is therefore protected only when a request is _partially_ served. The constant is also client-wide, and the single-request paths have no drain layer above them even in that partial case: a `Get`, a `Put`, a `TransactWriteItems` and **every** `queryAllPages` Query carry the throttle budget alone, and on those paths throttling arrives as a `ProvisionedThroughputExceededException` — a whole-request rejection with nothing partial to re-send — which now gets exactly one retry where it previously got three. That is precisely the exception ADR 0002 named when it sized its provisioned-capacity risk, and its "bounded, named risk rather than a whole class of failure" conclusion rests on two supports: the burst reserve and the alarm, and the SDK "retry[ing] automatically with exponential backoff and full jitter — 4 attempts". #122 removed half of one support without revisiting the argument, and the ADR text still states the 4. The exposure is not uniform: the ADR calls the synchronous dashboard fan-out the only genuinely user-visible throttle path, and that path is a per-site read fan-out over provisioned capacity, so it is the one where a halved retry budget converts a throttle into a user-visible failure rather than into latency. Two honest fixes, and the choice is a real one: per-path retry policy (a client whose budget is sized for drained partial failures, and one sized for whole-request throttles — which means more than one client configuration, currently a deliberate single seam, and the wholly-declined batch above shows the split is not simply batch-versus-single-request), or a re-derivation showing ADR 0002's argument still holds at one retry, in which case the ADR's own arithmetic needs updating to say so. A third throttle shape, found in review cycle 3, is worse than either and constrains that choice: the weather adapter's `TransactWriteItems` (`packages/storage/src/adapters/weather/weather-adapter.ts`). When DynamoDB cancels an in-flight transaction for capacity it raises no throttling exception at all — it answers `TransactionCanceledException`, with the cause reachable only inside `CancellationReasons[].Code` as `ProvisionedThroughputExceeded` or `ThrottlingError`. Neither retry mechanism can see that: in the installed `@aws-sdk/client-dynamodb` 3.1098.0 the generated `TransactionCanceledException` carries no `$retryable` trait — `ReplicatedWriteConflictException` in the same generated file does, so the omission is the service model's rather than a codegen artifact — and `@smithy/core` 3.31.1's `THROTTLING_ERROR_CODES` lists `ProvisionedThroughputExceededException` and `TransactionInProgressException` but not `TransactionCanceledException`. A capacity-cancelled transaction therefore gets **zero** retries, from either layer. That is not a #122 regression — it was zero at four attempts too — which is precisely why it belongs in this entry rather than in the diff that found it: the collapse did not cause it, but the decision this entry owns cannot be taken without it, because raising or splitting an attempt count does nothing whatsoever for a shape the SDK never classifies as retryable. Covering it means a different kind of change from tuning `STORAGE_MAX_ATTEMPTS` — inspecting `CancellationReasons` at the adapter and re-issuing there, or fitting the client with a custom retry classifier — so the per-path-policy option above is not a superset of it. `client.ts`'s doc block lists this path under the rule that any command not draining `UnprocessedItems` "has the SDK layer as its only retry layer", which is one layer too generous for this shape and wants correcting alongside whichever fix is chosen. Distinct from the "API's 15 s timeout" entry above, which is about how long one invocation may run; this is about whether a throttled read succeeds at all, and the two pull in opposite directions — more attempts is exactly what that entry cannot afford.

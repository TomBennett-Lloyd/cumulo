# Tech-debt log

A **buffer, not an archive**. `/review-loop` appends SYSTEMIC findings here instead of iterating on them; `/triage` periodically clusters entries, files root-cause GitHub issues, and **deletes** what it captured. A long-lived entry here means triage is overdue.

Entry format:

```
## YYYY-MM-DD — short title
- Where: file/module references
- What: the pattern or problem (symptom AND suspected root cause if known)
- Source: PR/issue #
```

Pointers must survive unrelated edits: cite **files and symbol or section names** (function names, headings, config keys, script names) — never bare line numbers, and never a copied code literal unless the literal itself is the finding. An entry that pins its claim to `file.sh`:42 sends its reader to whatever happens to sit at line 42 months later. Applies to entries dated 2026-07-31 onward; the back catalogue is retrofitted opportunistically, whenever an entry is edited for any other reason.

## 2026-07-30 — `aws_budgets_budget.cost_types` left at AWS defaults

- Where: `infra/bootstrap/budget.tf` (`aws_budgets_budget.monthly_cost_ceiling`)
- What: no `cost_types` block, so the budget uses the AWS defaults, which subtract credits and refunds. On an account carrying promotional credits the meter can therefore run well past $100/month of gross usage while net cost stays under threshold and nothing alerts — the alarm reports what will be billed, not what is being consumed. That is a defensible reading of "cost ceiling" for a project whose ceiling is about the bank balance, and it is the current deliberate choice; it stops being defensible the moment credits land on the account, because the whole point of the ceiling is to catch runaway usage _before_ it is expensive. Revisit if credits appear (or before any AWS-credits programme is used for this project): either add `cost_types { include_credit = true, include_refund = false }`, or add a second usage-oriented budget beside the billed-cost one. Not a fix for this diff — it is a policy decision about what the number means, and it wants the account's credit state as an input.

- What: light `--color-accent` #2a78d6 measures 4.30:1 on `--color-surface` and 3.92:1 on `--color-bg` — below WCAG AA's 4.5:1 for small text, which `--text-xs` link text certainly is. This predates #265 and is app-wide; the palette's approved record passes because the `dataviz` validator's checks are about categorical separation and the surfaces it was run against, not about small-text AA for the accent hue. The credits half of this is **resolved** and is not what remains: #265 decoupled both credit links from the accent (muted ink plus a permanent underline, `packages/ui/src/attribution/attribution.css` and `.map-attribution-tiles a`), which clears AA on the veil and would have been the right treatment on an opaque surface too. What is left is every other accent-on-surface link, the About dialog's source list being the one that ships today — so the dialog now renders its own composed Open-Meteo credit in the new treatment beside accent links in the old one, a visible mismatch that resolves when this does. The trap worth keeping for whoever picks it up: tuning a translucent surface upward cannot rescue an ink that already fails on the opaque version of that surface — the mix's ceiling is 4.30:1, so the ink has to change, not the background. Wanted: darken `--color-accent` in light mode until it clears 4.5:1 on both surfaces and re-run the palette validation, or adopt the underlined-muted treatment app-wide for small-text links, or record an explicit AA exception. Design-system decision with app-wide reach, which is why #265's layout chunk fixed only the links it had made illegible.

## 2026-08-05 — The token gallery renders two colour tokens as chips with no colour

- Where: `apps/web/src/preview/TokensHarness.tsx` (the swatch list and its `[data-token='--name']` keyed rules in `apps/web/src/preview/preview.css`), for `--color-surface-veil` and `--color-focus-ring`; the test that does not notice is `TokensPreview.test.tsx`
- What: the gallery's whole job is to display the design system, and two colour tokens are displayed as an empty chip — `preview.css` has no `[data-token='--color-surface-veil']` or `[data-token='--color-focus-ring']` rule painting the swatch, so the name renders with a blank square beside it. `TokensPreview.test.tsx` checks that every token _name_ appears, which is why the gap is silent: the page is complete by the only measure anything takes of it. The veil makes it worse than cosmetic, because a veil is precisely a token whose point is what it looks like over something — a flat chip could not show it even if one existed, so the honest rendering is a swatch over a patterned or image backdrop. Wanted: paint the two missing swatches (the veil over a backdrop that reveals its translucency), and strengthen the harness test from "every name is listed" to "every listed colour token resolves to a non-empty computed background" — the second half is the ratchet that stops the next token joining them. Note the test half may need the browser lane: jsdom applies no stylesheet, so a computed-background assertion has nowhere to run under vitest.
- Source: #265 review cycle 1 (layout)

## 2026-08-05 — The app's two native dialogs disagree about whether a modal names itself

- Where: `apps/web/src/add-site/AddSiteDialog.tsx` (the `<dialog className="add-site-dialog">` element) against `apps/web/src/header/AboutDialog.tsx` (which sets `aria-labelledby` from its own `useId`); the heading that would name the add-site one is `AddSiteForm`'s `.add-site-title`, whose id is generated by that component's `useId` and not exposed
- What: the add-site dialog carries no accessible name, so a screen reader announces it as an unnamed dialog; the About dialog beside it announces its heading. Two implementations of the same pattern now answer the same question differently, which is the part that makes this debt rather than a one-off gap — the next dialog copies whichever it lands on. The immediate reason is structural rather than an oversight: `AddSiteDialog` wraps a form it does not own the heading of, and the two available workarounds are both worse than the gap — an `aria-label` here would be a second copy of the words "Add a site" free to drift from the heading it restates (`structure.md` rule 7), and reaching into the form for its generated id is not a surface the form offers. The clean fix is `AddSiteForm` accepting a `titleId` (or exposing one), which makes the dialog's `aria-labelledby` point at the real heading and costs one prop; it was out of scope for #265 C6, which was scoped to wrap the form unchanged. Mitigated but not closed today: the form's mount effect focuses that heading, so the subject is the first thing announced on arrival. Worth settling as one convention for both dialogs rather than per component, since the a11y-linting gap logged above would not catch either.
- Source: #265 review cycle 1 (map controls)

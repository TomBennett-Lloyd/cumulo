# React standards

**Trigger:** writing or modifying a React component, hook, or anything involving `useEffect`.

## Rules

1. **Effects synchronize with external systems — nothing else.** Subscriptions, imperative map/chart APIs, timers. Not derived state (compute it during render), not responding to user actions (that's an event handler), not "run this when X changes" choreography (restructure so the data flows down).

2. **`react-hooks/exhaustive-deps` is an error, and the dependency array is never the knob.** If honest dependencies cause an infinite loop or unwanted re-runs, the _structure_ is wrong. The fixes, in order of preference:
   - Derived value? Compute during render; `useMemo` only if measured as expensive.
   - Responding to an interaction? Move the logic into the event handler.
   - Need the latest value inside an effect/callback _without_ re-triggering it? Store it in a ref, updated on render:

     ```ts
     const onSettledRef = useRef(onSettled);
     onSettledRef.current = onSettled;
     useEffect(() => {
       const sub = stream.subscribe((v) => onSettledRef.current(v));
       return () => sub.unsubscribe();
     }, [stream]); // honest deps — callback changes don't resubscribe
     ```

   - Unstable object/function dep? Stabilize it at its source (`useCallback`/`useMemo` there, or move it out of the component), don't omit it here.

3. **Colocate state; lift it only when two components genuinely share it.** Server data is not component state — it belongs to the data-fetching layer (query library, decided when `apps/web` lands), with loading/error modes encoded as a discriminated union (see `typing.md` rule 4).

4. **Components are presentational by default.** Data fetching and domain logic live in hooks/modules; a component that's hard to render in isolation (Storybook-style) is structured wrong.

5. **Design tokens only — lint-enforced, not a convention.** `no-restricted-syntax` in `eslint.config.mjs` and `stylelint.config.mjs` are the rule; read them for the exact scope rather than trusting a paraphrase here. Both run under `pnpm lint`, `packages/ui/src/tokens/tokens.css` is the one exempt file, and disable comments are themselves errors in both linters. So: if a token is missing, the lint error _is_ the design signal — raise it as a design-system issue rather than reaching for a literal.

## Async surface convention (apps/web)

Every surface that waits on data says so the same way — panels, the map region, the app boundary and the add-site form alike. The three states are implemented once in `apps/web/src/dashboard/panel-states.tsx` (`PanelPending`, `PanelEmpty`, `PanelError`), and the app's async-state and failure wording lives in `apps/web/src/dashboard/state-copy.ts` — reach for those rather than writing a fourth spelling of "loading…". Chart _chrome_ wording (the words a chart says about itself, like its clock) has its own owner, `apps/web/src/charts/chart-copy.ts`, a deliberate sibling. `apps/web/src/dashboard/state-copy-contract.test.ts` sweeps the app for phrase classes that drift back inline, so an inlined pending label or failure sentence fails a gate, not just a review.

- **Pending** is a visible label inside an `aria-busy="true"` container — never a live region mounted with its text already in it. A `role="status"` that exists only while it is full has no change to report, so it announces nothing and merely looks accessible (#161).

  **Amended 2026-08-12 by the owner (#448, design round 3 item 1): a surface that _is_ a drawing may carry its pending state as a drawing inside the `aria-busy` container, and then owes no visible label.** The forcing case is the fleet chart, whose pending label the owner ruled both misleading and a cause of the page jumping — _"graph loading state needs to be visual not words"_ — and whose replacement is a curve traced inside the plot's own box (`docs/design/chart-treatment.md`'s Loading section). It is the same shape of amendment as the two D3 ones below: the **visible label** clause is what gave way, and the property it was protecting did not. That property is the whole of what the bullet now asks — the busy state is machine-readable, and no live region mounts with text already in it. Both halves still bind here: `aria-busy` is not optional, so a wordless pending state is silent to eyes and not to a screen reader; and a drawing is not a licence to announce instead, because a `role="status"` mounted full announces nothing however the surface is styled.

  The exception is narrow on purpose, and the test is whether the surface's _content_ is a drawing rather than whether it happens to contain one. A panel of prose that grows a spinner has not earned it: the reader is waiting for words, so the wait is owed words. And a non-data state that is **text-bearing** is not covered by this at all — it stays a live region under the **Failed** bullet below, which is the announcement route a wordless pending state deliberately does not take.

- **Failed** is `role="alert"` with a message in the panel's own words, plus a retry **only when retrying can work**. These components mount into a tree that is already on screen, so the alert really is a change and really is announced. A retry that re-runs an identical metered request is not a recourse — omit it and let the reader's own controls be the retry.
- **Empty** is plain content, no live semantics, stating the next action where there is one. An empty fleet is a successful answer, not an event.
- **At most one live region per panel, with exactly one sanctioned co-occurrence.** Announcements compete; two regions in one panel means the reader hears whichever won. In a panel showing a chart, the region that budget is spent on is the chart's own readout (`.forecast-chart-readout`, `docs/design/chart-treatment.md`) — mounted empty with the chart and filled only when a reader moves the selection, so the budget goes to the sample the reader asked for. The one exception is the **failed** state, where a second `role="alert"` mounts beside that readout in the same panel — since #452 the chart's own in-figure `.forecast-chart-error` overlay (`charts/forecast-chart-error.tsx`), which is where a total failure of the chart's data path is now accounted for, rather than a `PanelError` above the plot. It is allowed because the two provably cannot compete: a failed fleet read leaves the chart no points, so the readout has no sample to render and stays empty for exactly as long as the alert is up. It is a co-occurrence, not a second budget — a panel wanting a live region for anything else still has none to spend. #284 D3 forced it by making the chart structural, so the failed arm no longer returns _instead_ of the chart; that is the same forcing event as the first-paint bullet below and the same shape of amendment, in which the literal count gave way and the property it protected — that a reader is never made to arbitrate between two things talking at once — did not.
- **Completion is not announced.** The arrival of data is the busy container being replaced by the content — that is the signal, and adding a "loaded" announcement on top of it says the same thing twice.
- **A live region never renders inside a `hidden`/`display: none` subtree** — it was never on screen, so the later reveal is an attribute change rather than a DOM change and assistive technology reports nothing at either moment (#161). A panel that can be hidden therefore renders its states only once it is revealed. `apps/web` has no such panel today: the fleet panel was the motivating one and stopped being hidden when the reading stopped swapping (#265), which is a reason the rule is easy to reintroduce unnoticed rather than a reason to drop it.
- **A message mounted in response to something the reader did is `role="alert"`** — the add-site refusal arrives because a button was pressed, so it really is a change to a tree already on screen.
- **First paint mounts no live region carrying text** — pending is `aria-busy` and alerts arrive only as changes, pinned by `Dashboard.test.tsx`'s "first paint mounts no live region carrying text". The property being protected is #161's: an announcement reaches a reader only by _arriving_, as a change to a region that was already there, so a region mounted with its text already inside it announces nothing and merely looks accessible. An **empty** region at first paint is the opposite case — it is the container a later change needs in order to be a change, and it says nothing on the way in. This rule counted regions rather than text until #284 D3, which made the fleet chart structural: the panel now renders one `.forecast-chart-figure` in every state, including the state first paint is in, so `.forecast-chart-readout` is on screen from the first frame. It arrives empty and stays empty until a reader moves the chart's selection — exactly what the bullet above requires of it — so the literal count is what gave way, not the property. A region that mounts _with_ text in it still fails this rule, and that is the whole of what it now asks.
- **An unhandled promise rejection lands at `AppErrorBoundary`**, which gives the rejection nobody awaited the same labelled failure a render throw gets rather than a silent hang.

The map shell composes `MapSurface` (`apps/web/src/map/MapSurface.tsx`) — one column behind the live canvas, the loading placeholder and the load failure — and its placeholder is the same `aria-busy` pending treatment, not a fourth spelling of it.

**Whether a selection is the reader's is a fact worth carrying, even though no selection moves focus.** A surface that opens because somebody pressed something is a change they asked for — a marker press, a search hit and a creation all qualify, and so does whatever opener is added next, because the test is that the page changed in answer to an action. A surface that opens because the URL said so asked nobody: the selected site's card mounts when the fleet listing resolves, which on a `?site=` link can be seconds in, so anything that surface does to the focus is done to somebody who did nothing to ask for it (WCAG 3.2.5). That asymmetry is the settled answer to [#260](https://github.com/TomBennett-Lloyd/cumulo/issues/260), and what it decides today is the capture-and-restore below rather than a landing. `Dashboard` carries the distinction beside the selection itself (`dashboard/selection-origin.ts`) rather than letting each surface guess.

**Where the focus lands on a selection is nowhere.** This paragraph has twice named an element instead — the card's own heading, then a control in the panel below the map — and #328 settled it at neither, on the rule that a page which grabs the focus takes the reader's place away to tell them something it could have told them where they stood (`design.md` rule 11; `docs/design/design-principles.md` carries the history). A selection's answer is announced by its own structure, and the reader is left where they put themselves. The site's name is carried by the card's `aria-labelledby` and by the row the fleet chart's legend grows under that name once the site's line is drawn — not by the chart's readout, which mounts empty and fills only when a reader moves the chart's selection (the live-region bullet above) — and the header's search additionally announces its hit in its own status region, which is what a search selecting something off screen otherwise says nothing about. Combobox discipline is the sharpest case and the one that named the change: picking a value keeps the focus in the input, so a landing elsewhere took the reader out of a field they were still typing in. The one exception is a **modal**, which keeps its heading landing — the add-site dialog is the surface whose own controls _are_ the answer, everything the reader came for is inside it, and while it is up there is nothing behind it to be left standing on.

**A surface that leaves owes a landing, and it owes it to whoever it took the focus from.** The site card captures `document.activeElement` as it opens and restores it on unmount, so a reader who came into the card and pressed Close lands back on the marker or the search input that opened it, without the dashboard knowing which happened. The capture happens inside the mount effect, after React has flushed the commit's unmount cleanups, which is what makes a newly created site's captured opener the map's add-site control rather than a submit button that has already left the document. An opener no longer in the document is not chased.

**A surface that never took the focus returns none, and since #328 that is the common case rather than the corner one.** It is one clause of the rule above and not a second rule: the card's restore is guarded on the card still holding the focus it would be giving back. With nothing landing a reader inside it, the card usually holds nothing, so a dismissal from outside it — another marker, a search hit — leaves the reader exactly where they already were instead of yanking them to the map. The hand-back is still owed and still fires for the reader who came _into_ the card, which a pointer press on Close does for free and a keyboard reader does by tabbing to it. Nothing about the mechanism changed when the landing went; it is the guard doing what it was written to do, which is why the guard is the thing to preserve rather than the count of paths that reach it.

**A modal owes its own landing, because the platform stops paying it.** The add-site draft is a `<dialog>` over the page and closes by being unmounted — a removed dialog never runs the close steps, so the browser's usual focus restoration never happens. It returns focus to the map control that opened it, from the dialog's effect cleanup rather than its `cancel` handler: on the Escape path the browser is still restoring focus while `cancel` is dispatched, and would overwrite a focus set there. That return is now the last focus move a creation makes, since the card mounting behind it takes none.

`Dashboard.focus.test.tsx` and `map/SitePopoverCard.test.tsx` hold all of this as far as `document.activeElement` goes. The ring a reader actually sees is a judgement about _how_ the focus arrived — the browser's own heuristic normally, and the element's focus-source guard where that heuristic gets a pointer focus wrong — so it is the browser lane's either way, and there it is two specs holding one clause each: `e2e/keyboard-focus.spec.ts` keeps the ring a keyboard reader depends on — on a site's marker on the map and on the fleet chart, and the deep link arriving over a real network with it — while `e2e/pointer-focus.spec.ts` keeps the other clause, that no ring appears where the reader did not ask for one, over both pointer flows: mouse **and touch**, named as two arms. The touch arm is #440's, and naming it rather than writing "pointer" is the point — "pointer" is the word that let the touch path go unmeasured while a tapped chart took a ring the mouse path never took. Neither is meaningful alone, since each one's assertions are satisfied by an app that fails the other's, so a change deleting either is deleting half a rule.

## Why

The effect-dependency hack is the canonical example of suppressing a symptom instead of fixing a cause: the lint rule is reporting a data-flow problem, and deleting the dependency converts a visible loop into a subtle stale-closure bug. The same root-cause principle applies to the whole component layer.
